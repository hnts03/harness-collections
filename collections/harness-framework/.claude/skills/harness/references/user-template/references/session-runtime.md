## 세션 시작

- 트리거 시 반드시 **resume detection**을 먼저 수행한다. 순서:
  1. `NEXT_PLAN_NO` 채번 (아래 규칙 참조)
  2. `CLAUDE.md` 읽기 → `## 완료된 세션 이력`으로 이전 이슈 맥락 파악. 의존성 있는 이슈라면 이 정보를 미션 명확화에 활용한다.
  3. `_workspace/*/*-dev-plan.md` 확인 → 진행 중 플랜 있으면 유저에게 이어서/새로 시작 여부 확인
- **플랜 넘버 채번 규칙 (resume detection 최우선 단계)**:
  - `_workspace/` 하위 플랜 디렉토리에서 `<NNN>` 부분만 추출하여 최댓값 + 1. 디렉토리가 없으면 `001`. 형식: 3자리 제로패딩.
  - 인정되는 디렉토리 형식: `<NNN>`(기존) 또는 `<NNN>-<short-job-description>`(신규). 예: `_workspace/001/`, `_workspace/006/`, `_workspace/007-workspace-rename/`.
  - 예: `_workspace/006/`, `_workspace/007-workspace-rename/` 존재 → 다음 플랜 넘버 `008`.
  - **이 값(`NEXT_PLAN_NO`)을 먼저 확정한 뒤**, 기존 플랜 파일(`*-dev-plan.md`) 검사를 수행한다. 어떤 분기를 타든 플랜 번호가 `001`로 초기화되지 않도록 한다.
- **플랜 디렉토리 명명 규칙**:
  - 신규 플랜 디렉토리는 `_workspace/<NNN>-<short-job-description>/` 형식으로 생성한다.
  - `<NNN>`: 3자리 제로패딩 정수.
  - `<short-job-description>`: 케밥케이스. 영문 소문자·숫자·하이픈만 허용. 작업 핵심을 담은 명사구. **2~5단어 / 영문 30자 이내** 권장. 첫·끝 하이픈 금지, 연속 하이픈 금지.
  - **dev-plan 파일명은 `<NNN>-dev-plan.md`** (디렉토리명의 `-<short-job-description>` 부분을 포함하지 않는다).
  - 예: `_workspace/007-workspace-rename/007-dev-plan.md`.
  - 기존 `<NNN>` 단독 형식 디렉토리는 그대로 인정하되, 신규 생성은 새 형식으로만 한다.
- **식별자(`<short-job-description>`) 도출 절차**: PM은 STEP 1 미션 명확화로 한 줄 목표 문장을 확정한 직후, 그 목표를 기반으로 후보 1~3개를 도출하여 유저에게 제시하고 확정받은 뒤 디렉토리를 생성한다. 유저가 미션과 함께 식별자를 직접 제시하면 형식 규칙 검증 후 즉시 사용한다. PM은 식별자를 단독으로 결정하지 않는다(공통 운영 원칙 적용).
- 작업 시작 전 `<플랜번호>-dev-plan.md` 파일에 계획과 현재 진행상황을 기록한다. 플랜 넘버는 하네스 팀이 재사용될 때 각 세션의 플랜을 구별하기 위한 식별자다.
  - **`dev-plan.md` 구조** — 아래 구조를 따른다. 이 파일은 PM이 task마다 직접 갱신하는 live document다.

    ```markdown
    ## 목표
    [세션의 목표]

    ## 팀 구성
    - 아키텍처 패턴: [선택된 패턴]
    - 에이전트: [역할 — 모델 목록]

    ## 작업 단계 및 현황

    ### [작업 단계 이름 — 의미 있는 서술형 명칭]
    **상태**: 대기 / 진행 중 / 완료
    **목표**: [이 단계의 목표]
    **담당**: [에이전트]

    #### Tasks
    - [ ] [서술형 task 식별자] — [담당] — 대기
    - [~] [서술형 task 식별자] — [담당] — 진행 중
    - [x] [서술형 task 식별자] — [담당] — 완료

    ### [다음 작업 단계 이름]
    ...

    ## 현재 상태
    - **진행 중인 단계**: [단계 이름]
    - **진행 중인 Task**: [task 식별자]
    - **다음 작업**: [다음 task 식별자 또는 다음 단계 이름]

    ## 이슈 / 결정 사항
    - [날짜] [내용]
    ```
- **task 식별자는 반드시 서술형으로 작성한다.** `task 1`, `task 2`, `T1`, `G2`처럼 의미를 담지 않는 단순 번호·코드네임은 금지한다. 작업 자체의 의미를 담은 명칭을 사용한다(예: `harness-skill-template.md 변경 사양 도출`, `design-spec 작성`, `qa-validate-trigger`). 의미 약어가 명확한 케밥케이스 식별자(`recon-agents`, `qa-trigger-test` 등)는 허용한다. 이 규칙은 dev-plan.md, _workspace 하위 산출물, 에이전트 간 메시지, 유저 대상 보고 모두에 적용된다.
- 팀원 간 소통 및 작업 도중 문서화가 필요한 경우 `_workspace/<플랜 디렉토리>/` 디렉토리 안에서 작업공간을 격리하여 관리한다. (`<플랜 디렉토리>`는 위 명명 규칙에 따라 `<NNN>` 또는 `<NNN>-<short-job-description>`이다.)
- 계획 수립 시 모호한 부분이 있거나, 작업 방향·구조·해결책에 대한 결정이 필요하면 무조건 유저와 align을 맞추고 이어서 진행한다. PM 단독으로 방향성을 결정하지 않는다.

## 작업 실행

- PM이 구성한 plan의 작업은 **작업 단계**(큰 단위)와 그 하위 **task**(세부 단위)로 스케줄된다. (에이전트 내부 협업 시 작업 단계를 "phase"로 호칭할 수 있으나, 유저 대상 텍스트와 dev-plan.md의 상위 구조 헤더에서는 사용하지 않는다.)
- 상호 의존성 없는 작업들은 병렬로 실행한다. 각 작업 간 의존성 체크를 사전에 수행해야 한다. **병렬 스폰 전 `outputs.files` 겹침을 반드시 확인한다 — 파일이 겹치는 task는 순차 실행.**
- **Task 분해 원칙**: 하나의 task는 단일 concern, 수정 파일 최대 3개를 기준으로 한다. 범위가 넓으면 subtask로 분해하여 각각 별도 worker에게 할당한다. worker를 더 많이 쓰더라도 각 worker의 범위를 좁게 유지한다.
- **작업 도중이라도** 모호한 요구사항·설계 결정·판단 기준이 생기면 즉시 유저에게 질문하여 align을 맞추고 진행한다. 불확실한 채로 진행하지 않는다.
- **task가 완료될 때마다** `dev-plan.md`의 task 체크박스와 `## 현재 상태` 섹션을 즉시 갱신한다. 이 갱신이 누락되면 resume detection이 부정확해진다.

## 실행 가시성 프로토콜

PM은 메인 컨텍스트에서 인라인 실행되므로, PM의 텍스트 출력이 사용자에게 직접 보인다. 반면 Agent tool로 스폰된 sub-agent 내부 작업은 사용자에게 보이지 않는다. 따라서 다음 보고를 **반드시** 수행한다:

| 시점 | 형식 |
|------|------|
| 단계 시작 | `--- 단계 시작: <단계 제목> ---` + 목표, 담당 |
| Agent 스폰 전 | `[<단계 제목>] <에이전트명> 스폰` + 목적, 예상 산출물 |
| Agent 완료 후 | `[<단계 제목>] <에이전트명> 완료 — <상태>` + 요약, 산출물 |
| 단계 완료 | `--- 단계 완료: <단계 제목> ---` + 결과, 다음 단계 |

이 4개 규칙은 모든 작업 단계에서 예외 없이 적용한다.

## Ad-hoc 직접 실행 원칙

PM이 sub-agent를 스폰하지 않고 직접 작업을 수행할 수 있는 조건:
- 단일 파일의 단순 텍스트 수정 (오타, 문구 변경, 섹션 추가 등)
- 판단이 필요 없는 기계적 작업 (상태 마킹, 체크박스 갱신 등)
- 수정 범위가 1~2개 파일 이내이고 변경 내용이 명확한 경우

직접 실행 시에도 dev-plan task에 반드시 아래 내용을 기재한다:

```markdown
- [x] task N — PM(직접) — 완료
  - 사유: <sub-agent 없이 직접 실행한 이유>
  - 변경: `<파일 경로>` — <추가/수정/삭제한 내용 요약>
```

task 체크박스를 `[x]`로 마킹할 때 변경 내역이 비어 있으면 안 된다.

## 실패 처리 정책

**기본 원칙**: 재시도는 최대 1회. 재시도 후 동일 실패 시 즉시 에스컬레이션하며 무한 루프를 허용하지 않는다. 모든 실패 내용은 `_workspace/<플랜 디렉토리>/failures.md`에 기록한다.

| 실패 유형 | 1차 대응 | 2차 대응 (재시도 후도 실패) |
|----------|---------|--------------------------|
| **worker 실패** | worker가 원인 분석 후 1회 재시도 | PM에게 에스컬레이션 |
| **reviewer reject** | worker가 피드백 반영 후 1회 재작업 | PM에게 에스컬레이션 |
| **QA fail** | 해당 task 담당 worker가 1회 수정 후 재검증 | PM에게 에스컬레이션 |

**PM 에스컬레이션 시 PM의 판단:**
1. PM이 대안 접근법을 직접 시도할 수 있으면 → 시도 (1회 한정)
2. 요구사항 명확화가 필요하거나 PM도 해결 불가 판단 시 → 유저에게 에스컬레이션

**유저 에스컬레이션 시 필수 포함 내용:**
- 무엇이 실패했는가 (실패 내용과 에러)
- 무엇을 시도했는가 (시도한 접근법)
- 무엇이 필요한가 (유저에게 요청하는 결정 또는 정보)

## 작업 단계 완료 시

- 각 작업 단계 완료마다 `docs/phase_<N>/` 디렉토리에 프로세스 진행 내용을 설명하는 마크다운 문서를 작성한다. (디렉토리 명명 규칙 `phase_<N>`은 기존 자산·`update-from-phase` 스킬과의 호환성을 위해 본 개정에서는 유지한다. 명명 변경은 별도 후속 작업으로 분리.)
- **`update-from-phase` 스킬을 트리거**하여 아래를 일괄 처리한다:
  - `dev-plan.md`: 해당 작업 단계를 `완료`로 마킹, 다음 작업 단계를 `진행 중`으로 전환
  - CLAUDE.md·memory 갱신
  - git commit(co-author 문구 제거) & push (연결된 remote repo가 있으면)
  > PM이 task마다 갱신한 dev-plan.md 내용은 유지하고, 작업 단계 상태만 덮어쓴다.

## 세션 종료

- 모든 작업 완료 후 `/clear`로 컨텍스트를 초기화하고 다음 작업을 준비한다.
- 유저가 별도 요구하지 않더라도 종료 시점에 CLAUDE.md·memory·관련 문서에서 현재까지의 context를 확인할 수 있어야 한다.
