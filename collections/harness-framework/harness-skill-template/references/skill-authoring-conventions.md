# 스킬 작성 컨벤션

### Cost test (비용 자문)

어떤 문장·섹션·스킬·에이전트도 추가하기 전에 "이게 없으면 에이전트가 실제로 잘못 동작하는가?"를 자문한다. 답이 "아니오"이면 추가하지 않는다. 이 원칙은 새 문장 추가, 새 스킬 생성, 새 에이전트 생성, 기존 문서 확장 등 모든 자산 변경 시점에 적용된다.

- 적용 시점: 새 문장·섹션·스킬·에이전트 추가 직전.
- 자문 기준: "유용해 보여서"라는 사유는 추가 근거가 되지 못한다. 잘못된 동작·실패 시나리오 1개 이상을 식별할 수 있어야 추가한다.
- 미통과 시 대응: 추가하지 않거나, 기존 문서·스킬의 확장으로 흡수한다.

### Description = routing trigger 3요소

스킬의 `description`은 사용자 쿼리에 대한 라우팅 신호로 작동한다. 신규 스킬·기존 스킬 description 변경 시 다음 **3요소**를 모두 포함해야 한다.

1. **트리거 시점 명세** — 이 스킬이 무엇을 하고, 사용자가 언제 이 스킬을 써야 하는가.
2. **트리거 키워드 목록** — 사용자가 쓸 법한 자연어 표현(공식적·캐주얼·영어 혼합·암시적 표현 등 최소 3종).
3. **트리거하지 않을 케이스** — 키워드가 유사하지만 다른 도구·스킬이 적합한 near-miss 경계 케이스.

나쁜 예: `"PDF 파일을 처리하는 스킬"`
좋은 예: `"PDF 읽기, 텍스트 추출, 병합, 분할, OCR 등 모든 PDF 작업을 수행한다. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것. 단순 텍스트 파일은 이 스킬을 트리거하지 않는다."`

좋은 예의 3요소 매핑:
- 트리거 시점 명세: `"PDF 읽기, 텍스트 추출, 병합, 분할, OCR 등 모든 PDF 작업을 수행한다"`
- 트리거 키워드: `".pdf 파일을 언급하거나 PDF 산출물을 요청하면"`
- 비트리거 케이스: `"단순 텍스트 파일은 이 스킬을 트리거하지 않는다"`

3요소 중 하나라도 빠지면 트리거 정확도가 떨어진다. `/harness-benchmark`로 검증한다.

**에이전트 description 축약 적용**: 에이전트의 description은 PM이 에이전트를 선택할 때 참조하는 메타데이터이지 `/` 트리거 신호가 아니다. 따라서 위 3요소 중 **트리거 키워드 목록 (받는 작업 유형)**만 핵심이다. 트리거 시점은 PM 라우팅 판단으로 흡수되고, 비트리거 케이스는 본문 STEP에서 다룬다.

### Eval-first 트리거 매트릭스

description을 작성하기 **전에** 트리거 케이스를 먼저 정의한다. Description은 이 매트릭스를 통과하도록 역설계한다.

매트릭스 구성 요건:
- **should-trigger 케이스 ≥ 5개** — 실제 사용자가 이 스킬을 호출할 법한 자연어 표현. 다양성을 확보한다(공식/캐주얼/영어 혼합/명시적/암시적 표현 최소 1개씩).
- **should-NOT-trigger 케이스 ≥ 2개 (near-miss 중심)** — 키워드가 유사하지만 이 스킬이 적합하지 않은 경계 케이스. **부정 예시가 긍정 예시보다 중요하다** (스킬이 자기 도메인 외 작업까지 흡수하는 라우팅 누수를 방지).
- **작성 위치** — `_workspace/<플랜 디렉토리>/trigger-matrix-<skill-name>.md`에 별도 파일로 작성하거나, 스킬이 작은 경우 create-skill의 STEP 0 인-라인 코멘트로 보존한다.

매트릭스 예시 형식:

```markdown
# 트리거 매트릭스 — <skill-name>

## Should-trigger (≥5)
1. "<자연어 쿼리 1>" — 사유: <왜 트리거해야 하는가>
2. ...

## Should-NOT-trigger (≥2)
1. "<near-miss 쿼리>" — 사유: <왜 다른 스킬·도구가 적합한가> — 대안: <트리거되어야 할 다른 스킬 이름>
2. ...
```

매트릭스 없이 description만 먼저 쓰면 라우팅 누수가 발생한다. 매트릭스를 먼저 작성한다. 사후 검증은 `/harness-benchmark` MODULE A(트리거 정확도 테스트)로 수행한다.

### Gotchas 섹션 컨벤션

운영 중 발견한 함정·예상치 못한 실패 케이스·재현 절차를 기록하는 표준 위치를 정의한다. **첫 함정 발견 전까지는 시드를 작성하지 않는다** (Cost test 적용 — 가설적 함정은 추가 근거가 되지 못한다).

- **작성 위치**: `claude-skills/<skill-name>/README.md`의 `## Gotchas` 섹션. README.md가 부재한 스킬에서 함정이 발견되면, 그 시점에 README.md를 신규 생성한다.
- **작성 시점**: 운영 중 함정이 1건 이상 실제로 발견되었을 때만. 가설적 함정은 작성하지 않는다.
- **작성 형식 (각 함정당)**:
  - **증상**: 실제로 관측된 잘못된 동작 1줄
  - **재현 절차**: 어떤 입력·환경에서 발생하는가
  - **원인**: 왜 발생하는가 (스킬 본문·description·외부 의존성 등)
  - **회피·완화**: 임시 대응(있는 경우)
  - **수정 PR/플랜 참조**: 영구 수정이 이루어진 경우 링크
- **부모 컨벤션과의 관계**: `collections/CLAUDE.md`는 README.md에 "사용법"·"설계 결정" 2개 섹션을 요구한다. `## Gotchas`는 이 두 섹션을 보충하는 3번째 섹션으로 추가하되, 함정이 없는 스킬은 섹션을 생략한다.
- **시드 범위**: 본 컨벤션을 정의하는 플랜에서는 README.md 시드를 수행하지 않는다(Gotchas 처리 범위 = "컨벤션만 정의"). 시드 작업은 별도 후속 플랜으로 분리하고, 기존 스킬에 대해서는 첫 함정 발견 시점부터 점진적으로 작성한다.

### Description 변경 시 재평가 의무

메인 브랜치에 머지된 기존 스킬·에이전트의 `description` 필드를 수정하는 경우, 다음을 의무화한다.

- **동일 PR/커밋에서 `/harness-benchmark`를 실행**하여 트리거 매트릭스 기반 정확도를 재측정한다.
- **벤치마크 보고서**(`_workspace/<플랜 디렉토리>/benchmark-<skill-name>.md`)를 PR 본문에 인용하거나 dev-plan.md에 첨부한다.
- **본문 수정만 있는 경우**(description 무변경)는 재평가 의무 없음. description은 라우팅에 직결되지만 본문은 트리거 결과에 영향이 적기 때문이다.
- **trigger-matrix-<skill-name>.md가 부재한 경우**: description 변경 PR에서 매트릭스를 동시에 작성하고 벤치마크를 수행한다.

이 규칙은 description = routing trigger 원칙("스킬 작성 컨벤션 → Description = routing trigger 3요소")의 운영 시점 적용이다. 본문 수정·리팩토링과 분리하여, description 변경은 별도 PR로 처리하는 것을 권장한다(작은 표면적·명확한 책임).

### 글로벌 컨텍스트 복제 금지 자문

신규 스킬·에이전트 생성 시 다음 3개 질문을 모두 확인한다. **하나라도 "예"이면 생성을 중단하고 유저에게 대안을 제안한다.**

1. 이 내용이 CLAUDE.md에 들어가야 할 **글로벌 지침**이 아닌가? (모든 세션에 항상 적용되어야 하는 운영 원칙이면 CLAUDE.md에 1줄 추가가 더 적합하다.)
2. 이 내용이 **단일 문장 프롬프트**로 대체 가능하지 않은가? (1~2줄로 끝나는 지침은 별도 스킬보다 인라인 처리가 비용 효율적이다.)
3. 이 스킬·에이전트가 정말 **독립 트리거 가치**가 있는가, 아니면 기존 스킬·에이전트의 확장으로 충분한가? (유사 자산 확장이 가능하면 신규 생성하지 않는다 — Cost test와 결합.)

자문 결과가 "예"인 경우의 대응:
- **글로벌 지침이라면**: 유저에게 "이 내용을 CLAUDE.md 운영 원칙에 1줄 추가하는 방향이 더 적합합니다"를 제안하고 생성을 중단한다.
- **단일 문장 프롬프트로 충분하다면**: "이 작업은 직접 프롬프트로 수행하거나 기존 스킬 본문에 추가하는 것이 적합합니다"를 제안하고 중단한다.
- **기존 자산 확장이 충분하다면**: 그 스킬·에이전트 이름을 명시하고 Edit 도구로 확장할 것을 제안한다.

본 자문은 "알리고 중단 제안" 강도다. 유저가 그래도 명시적으로 진행을 원하면 신규 생성을 허용한다(강제 거부 아님).

### 유저 대상 보고 — 메타정보 노출 제한

PM·에이전트가 사용자에게 직접 노출되는 텍스트에서는 마크다운 구현 디테일·메타정보를 그대로 노출하지 않고, **의미 단위(주제·영역·섹션 이름)**으로 추상화하여 보고한다. 핵심 변환: **마크다운 구현 단위(H2/H3, 줄 수, 헤더 개수) → 의미 단위(주제, 영역, 섹션 이름)**.

본 원칙은 기존 두 규칙의 상위 일반화다. 기존 두 규칙은 본 원칙의 구체 사례로 존속한다.

- **task 식별자 규칙** (`harness-skill-template/references/session-runtime.md` "세션 시작" 영역의 task 식별자 작성 규칙) = 본 원칙의 **식별자 사례**.
- **phase 용어 규칙** (`harness-skill-template/references/session-runtime.md` "작업 실행" 영역, 작업 단계 vs phase 호칭 분리) = 본 원칙의 **단일 용어 사례**.

#### 유효 컨텍스트 구분

본 원칙은 사용자에게 직접 노출되는 텍스트에만 적용한다. 기술 컨텍스트(설계 산출물·검증 보고서·에이전트 간 메시지·코드·메타 스킬 본문)에서는 헤더 위치·grep 패턴·라인 번호 등 마크다운 구현 디테일이 정확성을 위해 필요하므로 본 원칙을 적용하지 않는다.

| 컨텍스트 | 적용 | 비고 |
|----------|------|------|
| PM·에이전트가 사용자에게 출력하는 텍스트 | 적용 | 본 원칙의 핵심 |
| `dev-plan.md` (사용자가 직접 검토하는 산출물) | 적용 | 1차 노출 산출물 |
| AskUserQuestion 질문 본문·옵션 라벨 | 적용 | 사용자에게 직접 노출 |
| `design-spec.md` (설계 산출물) | 비적용 | grep 패턴·헤더 위치·라인 번호가 정확성 필수 |
| `qa-report.md` / `validate-report.md` | 비적용 | 검증 정확성 우선 |
| 에이전트 간 협업 메시지 (Worker Task Context 등) | 비적용 | 기술 컨텍스트 |
| 코드·스크립트 자체 | 비적용 | 구현 |
| 메타 스키마 표현 (`create-skill`·`create-agent` 본문의 frontmatter 설명) | 비적용 | 메타 스킬이 frontmatter 작성을 가르치는 곳 |

#### 위반 → 정상 변환 예시

마크다운 구현 단위가 등장하면 그것이 의미하는 내용(왜 그것이 등장했는가)을 식별하여 의미 단위 표현으로 교체한다.

- 위반: "`harness-skill-template.md` = 392줄, 26개 H2/H3 섹션"
  정상: "`harness-skill-template.md`는 팀 빌딩·세션 운영·스킬 작성 컨벤션·진입 가시성 등 여러 주제가 한 파일에 모여 있는 상태"
- 위반: "플랜 009에서 신설된 `## 스킬 작성 컨벤션` H2 (6개 H3, ~75줄)"
  정상: "플랜 009에서 추가된 스킬 작성 컨벤션 영역"
- 위반: "기존 컨벤션 ... 등 ~150줄이 한 파일 안에 공존"
  정상: "한 파일에 십여 개 주제가 모여 있어 분할 대상으로 적합"
- 위반: "신규 H2 `## Calling Context` 추가"
  정상: "신규 진입점 컨텍스트 섹션 추가"
- 위반(일반): AskUserQuestion 본문에 "`description` 필드를 수정합니까?"
  정상(일반): "이 스킬의 트리거 설명을 수정하시겠습니까?"
- 위반(일반): 사용자 보고에 "`-qF` 옵션으로 grep 검증 7건 통과"
  정상(일반): "검증 항목 7건 모두 통과"

#### 위반 발견 시 대응

PM·에이전트가 사용자 출력 직전에 자가 점검한다. 위반이 발견되면 출력 전에 의미 단위 표현으로 교체한다. 적절한 의미 단위가 떠오르지 않으면 **그 메타정보가 실제로 왜 등장했는가**(예: 줄 수를 보여주려는 의도가 "크다"인지 "주제가 많다"인지)를 먼저 식별한 뒤 그 의미를 평문으로 표현한다.

본 원칙은 Cost test와 동일한 적용 시점을 갖는다: 새 문장을 출력하기 직전. 추가 비용이 아니라 출력 검수 단계의 일부다.
