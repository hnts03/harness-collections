# harness 지시사항
> **🔧 `/harness` 전용 — `/pm`은 이 섹션을 실행하지 않는다.**
> 하네스 빌딩 시 1회 실행. 팀 구조·에이전트·스킬을 설계하고 생성하는 단계.

## 팀 빌딩 원칙

- 하네스는 reusable 해야 합니다. 처음에 팀 빌딩에 제시된 요구가 주어지지 않더라도 robust하게 작업을 할 수 있어야 합니다. 유저가 특정한 주제를 주었다 하더라도 그 업무에 편향되지 않도록 해야합니다.
- 하네스 구성의 개괄은 `/harness` 스킬 트리거 할 때 제공하나, 디테일한 매 작업 목표(이슈)는 `/pm` 스킬로 PM 에이전트를 트리거해서 유저가 직접 제공합니다. 그것을 바탕으로 작업 계획부터 실행, 리뷰, 테스트 자동화, QA, 문서화 프로세스가 완전히 구성될 수 있어야 합니다.
- 전문적으로 계획을 구성하고 태스크를 생성·관리할 수 있도록 PM 에이전트가 `/pm` 스킬로 트리거되어 실행되어야 합니다. 계획이 필요한 상황이라면 claude-code의 planner agent를 사용하여도 좋습니다.
- 테스트 자동화 프로세스까지 포함되어야 하고, 동일한 결과를 유저가 재생산할 수 있도록 가이드(WORKGUIDE)가 있어야 합니다.
- 팀 빌딩이 완료되면 **프로젝트 루트의 `WORKGUIDE.md`** 에 빌드된 팀의 사용법을 정리해두세요. (`docs/`는 생성된 산출물 디렉토리로 gitignore 처리되므로 WORKGUIDE는 루트에 위치해야 합니다.)
- 팀 빌딩 완료 시 **`CLAUDE.md`를 생성**한다. 팀 구성(에이전트·모델·역할), 스킬 목록, 운영 원칙을 기록하고 `## 완료된 세션 이력` 섹션을 빈 상태로 추가한다. 이후 `/update-from-phase` 스킬이 이 섹션에 세션 이력을 누적한다.

## 도메인 분석

팀 빌딩 전에 반드시 도메인 분석을 먼저 수행한다. 분석 결과는 패턴 선택과 역할군 구성의 직접적인 입력이 된다.

1. **도메인/프로젝트 파악** — 유저 요청에서 핵심 목적과 주요 작업 유형(생성, 검증, 편집, 분석 등)을 식별한다.
2. **재사용성 분석** — 이 팀이 반복적으로 처리하게 될 작업 유형을 파악한다. 특정 이슈에 편향되지 않는 범용 팀을 구성하기 위해 도메인의 공통 패턴을 추출한다.
3. **기존 에이전트/스킬 확인** — `.claude/agents/`와 `.claude/skills/`를 탐색하여 충돌·중복을 방지한다.
4. **코드베이스 탐색** (프로젝트가 있는 경우) — 기술 스택, 데이터 모델, 주요 모듈을 파악한다.
5. **분석 요약 도출** — 위 결과를 한 페이지로 요약한다. 이 요약이 다음 단계(패턴 선택, 역할군 구성)의 근거가 된다.

> **[체크포인트 1/4 — 도메인 분석 완료]**
> 핵심 작업 유형·재사용 패턴·기존 에이전트/스킬 현황을 한 페이지 요약으로 유저에게 제시한다. 확인을 받은 뒤 패턴 선택으로 넘어간다.

## 아키텍처 패턴 선택

도메인 분석 후 아래 기준으로 팀 아키텍처 패턴을 선택한다. **실전에서는 단일 패턴보다 복합 패턴이 흔하므로 조합도 적극 고려한다.**

| 패턴 | 선택 기준 |
|------|----------|
| **파이프라인** | 각 단계가 이전 단계 산출물에 강하게 의존하는 순차 작업 |
| **팬아웃/팬인** | 동일 입력에 대해 서로 다른 관점의 병렬 분석이 필요한 경우 |
| **전문가 풀** | 입력 유형에 따라 다른 전문가를 선택적으로 호출해야 하는 경우 |
| **생성-검증** | 산출물 품질 보장이 중요하고 객관적 검증 기준이 존재하는 경우 |
| **감독자** | 작업량이 가변적이거나 런타임에 작업 분배를 동적으로 결정해야 하는 경우 |
| **계층적 위임** | 문제가 자연스럽게 계층적으로 분해되는 구조 (최대 2단계 권장) |

**에이전트 팀 vs 서브 에이전트:**
- 2개 이상 에이전트가 협업하면 **에이전트 팀**이 기본값
- 에이전트 간 통신이 불필요하거나 단일 에이전트면 서브 에이전트

> 상세 기준·팀 모드 적합성·복합 패턴 예시는 `references/agent-design-patterns.md` 참조.

> **[체크포인트 2/4 — 아키텍처 패턴 확정]**
> 선택한 패턴(단일 또는 복합)과 선택 이유를 유저에게 제시한다. 패턴이 잘못되면 이후 역할군 구성 전체가 틀어지므로, 확인을 받은 뒤 에이전트/스킬 정의로 넘어간다.

## 역할군 및 스킬 구성 최소 만족 조건

하네스 빌딩 시 아래 조건은 반드시 만족해야한다. 그 외에 팀 운영 시 필요하다고 판단되는 경우 스킬과 에이전트를 직접 만들어서 사용한다.

### 에이전트

모든 agent는 각 분야에 대해 20년 이상의 경력자들이다.

- **project-manager** : 주어진 미션에 대응하여 high-level research를 수행하고 그것을 바탕으로 작업 plan 및 작업자들에게 업무를 분배·오케스트레이션 한다. 서브 에이전트들을 병렬화하여 업무를 처리시키며, 각 phase와 task 간 의존성을 사전에 파악하여 최적의 병렬 작업을 달성한다.
  - **[resume detection 필수]** 트리거 시 가장 먼저 아래 순서로 이전 세션 여부를 확인한다:
    1. **플랜 번호 먼저 확정**: `_workspace/` 하위 플랜 디렉토리(형식 `<NNN> 또는 <NNN>-<short-job-description>`)에서 `<NNN>` 부분만 추출하여 최댓값 + 1을 `NEXT_PLAN_NO`로 고정. 없으면 `001`. (채번 규칙: 아래 PM 운영 지침 참조)
    2. `_workspace/*/*-dev-plan.md` 파일 존재 여부 및 진행 상태 확인
    3. 진행 중인 플랜 발견 → 유저에게 이어서 진행할지 새로 시작할지 확인 후 분기
       - **이어서** → 해당 플랜 번호 유지 (`NEXT_PLAN_NO` 무시)
       - **새로 시작** → `NEXT_PLAN_NO` 사용
    4. 플랜 없음 → `NEXT_PLAN_NO`로 신규 세션 시작
- **architect** (optional) : 개발 업무의 경우 프로젝트 구조, 내부 컴포넌트 간 인터페이스, 외부 API 등 다양한 구조 정의를 사전에 구성한다. **직접 파일을 탐색하지 않고 worker를 fan-out 스폰하여 데이터를 수집**한 뒤, 취합된 결과만 보고 설계에 집중한다 (탐색 위임 패턴).
- **worker** : PM이 만들어둔 plan의 task를 실제 수행하는 에이전트로 개발·탐색 등 일반적인 업무를 담당한다.
  - **[Scope 자가진단 필수]** task 수신 즉시 아래 조건을 확인한다. 하나라도 해당하면 구현 미착수 상태로 `failed` 보고 후 분해 제안:
    1. `outputs.files` 수가 4개 이상이거나 건드릴 파일이 3개 초과로 예상될 때
    2. description에 복수의 독립적 concern이 혼재할 때 (예: "파싱 + 저장 + 알림")
    3. acceptance_criteria가 단일 task로 검증 불가할 만큼 넓을 때
- **reviewer** : worker의 작업을 리뷰한다. worker role이 개발이면 코드 리뷰, 탐색이면 정보 더블체크를 수행한다.
- **qa** : phase 단위의 QA를 수행한다. QA 완료 후 결과 보고서를 생성하여 PM이 확인하도록 한다.
- **document-writer** : 미션이 완료되었을 때 결과를 정리하는 문서를 생산한다.

### 스킬

- **pm** : project-manager 에이전트를 트리거하는 진입점 스킬. `/pm` 명령으로 호출하며, resume detection → 미션 수령 → 플랜 수립 → 오케스트레이션 전 과정을 시작한다.
- **create-skill** (optional) : 필요한 skill을 생성하는 skill이다. 이미 유사 skill이 존재한다면 생성하지 않아도 된다. 스킬 명세 파일명은 반드시 `SKILL.md`로 고정한다.
- **create-agent** (optional) : 필요한 agent를 생성하는 skill이다. 이미 유사 agent가 존재한다면 생성하지 않아도 된다.
- **clean-commit** : claude-code는 git commit 시 co-author 문구를 삽입한다. 이 문구를 제거하고, DCO `Signed-off-by` 서명을 삽입하여 commit하는 기능이다. 글로벌/로컬 git identity가 2개 이상 존재하면 유저에게 어느 identity를 사용할지 확인한다.
- **update-from-phase** : phase 완료 시 PM이 직접 트리거한다. dev-plan.md의 phase 상태 마킹, CLAUDE.md·memory 갱신, git commit & push를 일괄 처리한다. task 단위 갱신은 PM이 직접 수행하며 이 스킬은 덮어쓰지 않는다.

> **[체크포인트 3/4 — 팀 구성 확정]**
> 에이전트 목록(역할·모델), 스킬 목록을 유저에게 제시한다. 확인을 받은 뒤 실제 에이전트/스킬 파일 생성으로 넘어간다.

## harness 동작 재정의

- **SKILL.md 파일명 강제**: 현재 harness 스킬의 버그로 인해 skill creation 시 `skill.md`로 작성하는 버그가 있습니다. skill을 만들 때 반드시 `SKILL.md` 파일명으로 작업하도록 강제하세요.
- **모델 선택 기준**: 현재 harness 스킬은 모든 agent를 `opus`로 생성하지만, 역할 복잡도에 따라 아래 기준으로 모델을 선택한다.

  | 모델 | 역할 | 이유 |
  |------|------|------|
  | **opus** | project-manager | 전체 계획 수립·의존성 분석·오케스트레이션 결정 등 복잡한 판단 |
  | **opus** | architect | 시스템 구조 설계·인터페이스 정의 등 높은 추론 복잡도 |
  | **opus** | reviewer | 품질 판단·미묘한 결함 감지 등 섬세한 평가 능력 필요 |
  | **opus** | qa | 경계면 교차 비교·통합 정합성 검증 등 정확성이 핵심 |
  | **sonnet** | worker | 명확히 정의된 task 실행 중심. 비용 절감 효과 가장 큼 |
  | **sonnet** | document-writer | 구조화된 문서 작성으로 복잡한 추론 불필요 |

  > **예외**: worker라도 요구사항이 모호하거나 아키텍처 수준의 판단이 필요한 task는 `opus`로 업그레이드한다. 모델 선택은 역할 고정이 아니라 **task 복잡도 기반**임을 기억한다.

- **Worker 범위 강제 규칙**: PM은 worker 스폰 전에 아래를 반드시 검토한다.
  - 수정 파일 3개 초과 → subtask 분해 후 각각 별도 worker 스폰
  - concern 복수 → concern별 분리
  - 병렬 스폰 시 `outputs.files` 교집합 확인 → 겹치면 순차 실행

## 스킬 작성 컨벤션

### Cost test (비용 자문)

어떤 문장·섹션·스킬·에이전트도 추가하기 전에 "이게 없으면 에이전트가 실제로 잘못 동작하는가?"를 자문한다. 답이 "아니오"이면 추가하지 않는다. 이 원칙은 새 문장 추가, 새 스킬 생성, 새 에이전트 생성, 기존 문서 확장 등 모든 자산 변경 시점에 적용된다.

- 적용 시점: 새 문장·섹션·스킬·에이전트 추가 직전.
- 자문 기준: "유용해 보여서"라는 사유는 추가 근거가 되지 못한다. 잘못된 동작·실패 시나리오 1개 이상을 식별할 수 있어야 추가한다.
- 미통과 시 대응: 추가하지 않거나, 기존 문서·스킬의 확장으로 흡수한다.

### Description = routing trigger 3요소

스킬의 `description`은 사용자 쿼리에 대한 라우팅 신호로 작동한다. 신규 스킬·기존 스킬 description 변경 시 다음 **3요소**를 모두 포함해야 한다.

1. **트리거 시점 명세** — 이 스킬이 무엇을 하고, 사용자가 언제 이 스킬을 써야 하는가.
2. **트리거 키워드 목록** — 사용자가 쓸 법한 자연어 표현(공식적·캐주얼·영어 혼합·암시적 표현 등 최소 3종).
3. **트리거하지 않을 케이스** — 키워드가 유사하지만 다른 도구·스킬이 적합한 near-miss 경계 케이스.

나쁜 예: `"PDF 파일을 처리하는 스킬"`
좋은 예: `"PDF 읽기, 텍스트 추출, 병합, 분할, OCR 등 모든 PDF 작업을 수행한다. .pdf 파일을 언급하거나 PDF 산출물을 요청하면 반드시 이 스킬을 사용할 것. 단순 텍스트 파일은 이 스킬을 트리거하지 않는다."`

좋은 예의 3요소 매핑:
- 트리거 시점 명세: `"PDF 읽기, 텍스트 추출, 병합, 분할, OCR 등 모든 PDF 작업을 수행한다"`
- 트리거 키워드: `".pdf 파일을 언급하거나 PDF 산출물을 요청하면"`
- 비트리거 케이스: `"단순 텍스트 파일은 이 스킬을 트리거하지 않는다"`

3요소 중 하나라도 빠지면 트리거 정확도가 떨어진다. `/harness-benchmark`로 검증한다.

**에이전트 description 축약 적용**: 에이전트의 description은 PM이 에이전트를 선택할 때 참조하는 메타데이터이지 `/` 트리거 신호가 아니다. 따라서 위 3요소 중 **트리거 키워드 목록 (받는 작업 유형)**만 핵심이다. 트리거 시점은 PM 라우팅 판단으로 흡수되고, 비트리거 케이스는 본문 STEP에서 다룬다.

### Eval-first 트리거 매트릭스

description을 작성하기 **전에** 트리거 케이스를 먼저 정의한다. Description은 이 매트릭스를 통과하도록 역설계한다.

매트릭스 구성 요건:
- **should-trigger 케이스 ≥ 5개** — 실제 사용자가 이 스킬을 호출할 법한 자연어 표현. 다양성을 확보한다(공식/캐주얼/영어 혼합/명시적/암시적 표현 최소 1개씩).
- **should-NOT-trigger 케이스 ≥ 2개 (near-miss 중심)** — 키워드가 유사하지만 이 스킬이 적합하지 않은 경계 케이스. **부정 예시가 긍정 예시보다 중요하다** (스킬이 자기 도메인 외 작업까지 흡수하는 라우팅 누수를 방지).
- **작성 위치** — `_workspace/<플랜 디렉토리>/trigger-matrix-<skill-name>.md`에 별도 파일로 작성하거나, 스킬이 작은 경우 create-skill의 STEP 0 인-라인 코멘트로 보존한다.

매트릭스 예시 형식:

```markdown
# 트리거 매트릭스 — <skill-name>

## Should-trigger (≥5)
1. "<자연어 쿼리 1>" — 사유: <왜 트리거해야 하는가>
2. ...

## Should-NOT-trigger (≥2)
1. "<near-miss 쿼리>" — 사유: <왜 다른 스킬·도구가 적합한가> — 대안: <트리거되어야 할 다른 스킬 이름>
2. ...
```

매트릭스 없이 description만 먼저 쓰면 라우팅 누수가 발생한다. 매트릭스를 먼저 작성한다. 사후 검증은 `/harness-benchmark` MODULE A(트리거 정확도 테스트)로 수행한다.

### Gotchas 섹션 컨벤션

운영 중 발견한 함정·예상치 못한 실패 케이스·재현 절차를 기록하는 표준 위치를 정의한다. **첫 함정 발견 전까지는 시드를 작성하지 않는다** (Cost test 적용 — 가설적 함정은 추가 근거가 되지 못한다).

- **작성 위치**: `claude-skills/<skill-name>/README.md`의 `## Gotchas` 섹션. README.md가 부재한 스킬에서 함정이 발견되면, 그 시점에 README.md를 신규 생성한다.
- **작성 시점**: 운영 중 함정이 1건 이상 실제로 발견되었을 때만. 가설적 함정은 작성하지 않는다.
- **작성 형식 (각 함정당)**:
  - **증상**: 실제로 관측된 잘못된 동작 1줄
  - **재현 절차**: 어떤 입력·환경에서 발생하는가
  - **원인**: 왜 발생하는가 (스킬 본문·description·외부 의존성 등)
  - **회피·완화**: 임시 대응(있는 경우)
  - **수정 PR/플랜 참조**: 영구 수정이 이루어진 경우 링크
- **부모 컨벤션과의 관계**: `collections/CLAUDE.md`는 README.md에 "사용법"·"설계 결정" 2개 섹션을 요구한다. `## Gotchas`는 이 두 섹션을 보충하는 3번째 섹션으로 추가하되, 함정이 없는 스킬은 섹션을 생략한다.
- **시드 범위**: 본 컨벤션을 정의하는 플랜에서는 README.md 시드를 수행하지 않는다(Gotchas 처리 범위 = "컨벤션만 정의"). 시드 작업은 별도 후속 플랜으로 분리하고, 기존 스킬에 대해서는 첫 함정 발견 시점부터 점진적으로 작성한다.

### Description 변경 시 재평가 의무

메인 브랜치에 머지된 기존 스킬·에이전트의 `description` 필드를 수정하는 경우, 다음을 의무화한다.

- **동일 PR/커밋에서 `/harness-benchmark`를 실행**하여 트리거 매트릭스 기반 정확도를 재측정한다.
- **벤치마크 보고서**(`_workspace/<플랜 디렉토리>/benchmark-<skill-name>.md`)를 PR 본문에 인용하거나 dev-plan.md에 첨부한다.
- **본문 수정만 있는 경우**(description 무변경)는 재평가 의무 없음. description은 라우팅에 직결되지만 본문은 트리거 결과에 영향이 적기 때문이다.
- **trigger-matrix-<skill-name>.md가 부재한 경우**: description 변경 PR에서 매트릭스를 동시에 작성하고 벤치마크를 수행한다.

이 규칙은 description = routing trigger 원칙("스킬 작성 컨벤션 → Description = routing trigger 3요소")의 운영 시점 적용이다. 본문 수정·리팩토링과 분리하여, description 변경은 별도 PR로 처리하는 것을 권장한다(작은 표면적·명확한 책임).

### 글로벌 컨텍스트 복제 금지 자문

신규 스킬·에이전트 생성 시 다음 3개 질문을 모두 확인한다. **하나라도 "예"이면 생성을 중단하고 유저에게 대안을 제안한다.**

1. 이 내용이 CLAUDE.md에 들어가야 할 **글로벌 지침**이 아닌가? (모든 세션에 항상 적용되어야 하는 운영 원칙이면 CLAUDE.md에 1줄 추가가 더 적합하다.)
2. 이 내용이 **단일 문장 프롬프트**로 대체 가능하지 않은가? (1~2줄로 끝나는 지침은 별도 스킬보다 인라인 처리가 비용 효율적이다.)
3. 이 스킬·에이전트가 정말 **독립 트리거 가치**가 있는가, 아니면 기존 스킬·에이전트의 확장으로 충분한가? (유사 자산 확장이 가능하면 신규 생성하지 않는다 — Cost test와 결합.)

자문 결과가 "예"인 경우의 대응:
- **글로벌 지침이라면**: 유저에게 "이 내용을 CLAUDE.md 운영 원칙에 1줄 추가하는 방향이 더 적합합니다"를 제안하고 생성을 중단한다.
- **단일 문장 프롬프트로 충분하다면**: "이 작업은 직접 프롬프트로 수행하거나 기존 스킬 본문에 추가하는 것이 적합합니다"를 제안하고 중단한다.
- **기존 자산 확장이 충분하다면**: 그 스킬·에이전트 이름을 명시하고 Edit 도구로 확장할 것을 제안한다.

본 자문은 "알리고 중단 제안" 강도다. 유저가 그래도 명시적으로 진행을 원하면 신규 생성을 허용한다(강제 거부 아님).

# PM 운영 지침
> **🚀 `/pm` 전용 — 하네스 팀이 구성된 후 PM 에이전트가 매 세션(이슈)마다 따르는 운영 규칙.**
> `/pm`이 이 파일을 받으면 이 섹션만 참조한다. 위의 "harness 지시사항" 섹션은 무시한다.

## 세션 시작

- 트리거 시 반드시 **resume detection**을 먼저 수행한다. 순서:
  1. `NEXT_PLAN_NO` 채번 (아래 규칙 참조)
  2. `CLAUDE.md` 읽기 → `## 완료된 세션 이력`으로 이전 이슈 맥락 파악. 의존성 있는 이슈라면 이 정보를 미션 명확화에 활용한다.
  3. `_workspace/*/*-dev-plan.md` 확인 → 진행 중 플랜 있으면 유저에게 이어서/새로 시작 여부 확인
- **플랜 넘버 채번 규칙 (resume detection 최우선 단계)**:
  - `_workspace/` 하위 플랜 디렉토리에서 `<NNN>` 부분만 추출하여 최댓값 + 1. 디렉토리가 없으면 `001`. 형식: 3자리 제로패딩.
  - 인정되는 디렉토리 형식: `<NNN>`(기존) 또는 `<NNN>-<short-job-description>`(신규). 예: `_workspace/001/`, `_workspace/006/`, `_workspace/007-workspace-rename/`.
  - 예: `_workspace/006/`, `_workspace/007-workspace-rename/` 존재 → 다음 플랜 넘버 `008`.
  - **이 값(`NEXT_PLAN_NO`)을 먼저 확정한 뒤**, 기존 플랜 파일(`*-dev-plan.md`) 검사를 수행한다. 어떤 분기를 타든 플랜 번호가 `001`로 초기화되지 않도록 한다.
- **플랜 디렉토리 명명 규칙**:
  - 신규 플랜 디렉토리는 `_workspace/<NNN>-<short-job-description>/` 형식으로 생성한다.
  - `<NNN>`: 3자리 제로패딩 정수.
  - `<short-job-description>`: 케밥케이스. 영문 소문자·숫자·하이픈만 허용. 작업 핵심을 담은 명사구. **2~5단어 / 영문 30자 이내** 권장. 첫·끝 하이픈 금지, 연속 하이픈 금지.
  - **dev-plan 파일명은 `<NNN>-dev-plan.md`** (디렉토리명의 `-<short-job-description>` 부분을 포함하지 않는다).
  - 예: `_workspace/007-workspace-rename/007-dev-plan.md`.
  - 기존 `<NNN>` 단독 형식 디렉토리는 그대로 인정하되, 신규 생성은 새 형식으로만 한다.
- **식별자(`<short-job-description>`) 도출 절차**: PM은 STEP 1 미션 명확화로 한 줄 목표 문장을 확정한 직후, 그 목표를 기반으로 후보 1~3개를 도출하여 유저에게 제시하고 확정받은 뒤 디렉토리를 생성한다. 유저가 미션과 함께 식별자를 직접 제시하면 형식 규칙 검증 후 즉시 사용한다. PM은 식별자를 단독으로 결정하지 않는다(공통 운영 원칙 적용).
- 작업 시작 전 `<플랜번호>-dev-plan.md` 파일에 계획과 현재 진행상황을 기록한다. 플랜 넘버는 하네스 팀이 재사용될 때 각 세션의 플랜을 구별하기 위한 식별자다.
  - **`dev-plan.md` 구조** — 아래 구조를 따른다. 이 파일은 PM이 task마다 직접 갱신하는 live document다.

    ```markdown
    ## 목표
    [세션의 목표]

    ## 팀 구성
    - 아키텍처 패턴: [선택된 패턴]
    - 에이전트: [역할 — 모델 목록]

    ## 작업 단계 및 현황

    ### [작업 단계 이름 — 의미 있는 서술형 명칭]
    **상태**: 대기 / 진행 중 / 완료
    **목표**: [이 단계의 목표]
    **담당**: [에이전트]

    #### Tasks
    - [ ] [서술형 task 식별자] — [담당] — 대기
    - [~] [서술형 task 식별자] — [담당] — 진행 중
    - [x] [서술형 task 식별자] — [담당] — 완료

    ### [다음 작업 단계 이름]
    ...

    ## 현재 상태
    - **진행 중인 단계**: [단계 이름]
    - **진행 중인 Task**: [task 식별자]
    - **다음 작업**: [다음 task 식별자 또는 다음 단계 이름]

    ## 이슈 / 결정 사항
    - [날짜] [내용]
    ```
- **task 식별자는 반드시 서술형으로 작성한다.** `task 1`, `task 2`, `T1`, `G2`처럼 의미를 담지 않는 단순 번호·코드네임은 금지한다. 작업 자체의 의미를 담은 명칭을 사용한다(예: `harness-skill-template.md 변경 사양 도출`, `design-spec 작성`, `qa-validate-trigger`). 의미 약어가 명확한 케밥케이스 식별자(`recon-agents`, `qa-trigger-test` 등)는 허용한다. 이 규칙은 dev-plan.md, _workspace 하위 산출물, 에이전트 간 메시지, 유저 대상 보고 모두에 적용된다.
- 팀원 간 소통 및 작업 도중 문서화가 필요한 경우 `_workspace/<플랜 디렉토리>/` 디렉토리 안에서 작업공간을 격리하여 관리한다. (`<플랜 디렉토리>`는 위 명명 규칙에 따라 `<NNN>` 또는 `<NNN>-<short-job-description>`이다.)
- 계획 수립 시 모호한 부분이 있거나, 작업 방향·구조·해결책에 대한 결정이 필요하면 무조건 유저와 align을 맞추고 이어서 진행한다. PM 단독으로 방향성을 결정하지 않는다.

> **[체크포인트 4/4 — 플랜 확정]**
> 작성한 `<플랜번호>-dev-plan.md`(작업 단계 구성, 의존성, 담당 에이전트)를 유저에게 제시한다. 확인을 받은 뒤 실제 작업 실행으로 넘어간다.

## 작업 실행

- PM이 구성한 plan의 작업은 **작업 단계**(큰 단위)와 그 하위 **task**(세부 단위)로 스케줄된다. (에이전트 내부 협업 시 작업 단계를 "phase"로 호칭할 수 있으나, 유저 대상 텍스트와 dev-plan.md의 상위 구조 헤더에서는 사용하지 않는다.)
- 상호 의존성 없는 작업들은 병렬로 실행한다. 각 작업 간 의존성 체크를 사전에 수행해야 한다. **병렬 스폰 전 `outputs.files` 겹침을 반드시 확인한다 — 파일이 겹치는 task는 순차 실행.**
- **Task 분해 원칙**: 하나의 task는 단일 concern, 수정 파일 최대 3개를 기준으로 한다. 범위가 넓으면 subtask로 분해하여 각각 별도 worker에게 할당한다. worker를 더 많이 쓰더라도 각 worker의 범위를 좁게 유지한다.
- **작업 도중이라도** 모호한 요구사항·설계 결정·판단 기준이 생기면 즉시 유저에게 질문하여 align을 맞추고 진행한다. 불확실한 채로 진행하지 않는다.
- **task가 완료될 때마다** `dev-plan.md`의 task 체크박스와 `## 현재 상태` 섹션을 즉시 갱신한다. 이 갱신이 누락되면 resume detection이 부정확해진다.

## PM 호출 진입 가시성 원칙

PM은 사용자가 `/pm`을 직접 호출한 경우 외에도 외부 스킬(예: `/harness:harness`)에 의해 자동 호출될 수 있다. 자동 호출은 사용자가 PM 사용을 의식적으로 선택한 것이 아니므로, PM이 어떤 다른 행동(Resume Detection·미션 명확화 등)을 시작하기 전에 호출 사실 자체를 명시하고 동의를 받아야 한다. 이 원칙은 공통 운영 원칙(무허가 방향성 결정 금지)의 진입점 적용 사례다.

### 진입 분기 판별 메커니즘 (Hint 전달 방식)

`/pm` 스킬 SKILL.md에 진입점 indicator 라인을 평문으로 박아둔다. SKILL.md 본문은 사용자가 `/pm`을 직접 트리거한 경우에만 PM 컨텍스트로 펼쳐지므로, indicator 라인의 존재 자체가 "직접 호출" 신호가 된다. 외부 스킬이 PM을 호출할 때는 자기 SKILL.md만 펼쳐지므로 자연스럽게 부재가 된다.

- **Indicator 형식 (도메인별 placeholder)**: `<DOMAIN>_PM_ENTRY_POINT: direct (/<skill-name>)`
  - 본 하네스 프레임워크의 경우: `HARNESS_PM_ENTRY_POINT: direct (/pm)`
  - 도메인별 prefix(`<DOMAIN>_`)로 다른 프로젝트 PM과 우발적 매칭을 회피한다.
- **삽입 위치**: `/pm` SKILL.md의 `## 실행` 헤더 직전, 별도 H2 섹션(`## Calling Context`)에 둔다.
- **검사 위치**: PM 에이전트의 STEP 0(Resume Detection) 첫 동작 직전. STEP 0 [0단계]로 신설하여 [1단계] 플랜 번호 확정 이전에 분기를 결정한다.
- **매칭 방식**: 정확 일치(exact match). 부분 매칭은 외부 스킬의 우발적 매칭 위험이 있어 금지한다.
- **Fallback**: indicator 부재 = 비직접 호출(default). 외부 플러그인 호환성을 위한 의도된 동작.

### 비직접 호출 시 PM 절차

다음 순서를 어긴 어떤 동작(STEP 0 [1단계] 플랜 번호 확정, CLAUDE.md 읽기 등)도 indicator 검사 이전에 수행하지 않는다.

1. **자가 announce 메시지 출력** — PM이 호출되어 파이프라인이 시작되려 한다는 사실, 호출 컨텍스트(외부 스킬 추정), 파이프라인 단계 4개를 사용자에게 명시한다.
2. **AskUserQuestion 호출** — `예, PM으로 진행` / `아니오, PM 종료` 2개 옵션 제시. 진입 동의의 핵심 결정만 묻는다(작업 성격 분류 등 부차 절차는 STEP 1 미션 명확화에서 다룬다).
3. **사용자 선택 처리**:
   - `예` → STEP 0 [1단계]로 진행.
   - `아니오` → 종료 메시지 출력 후 즉시 종료. 대안(직접 도구 사용, 다른 스킬 호출, `/pm` 직접 재트리거)을 안내.

### 직접 호출 시 PM 동작

Indicator 발견 시 가시화·동의 절차는 모두 생략하고 STEP 0 [1단계]로 직진한다. 다만 한 줄 안내(`(PM 직접 호출 모드 — \`/<skill-name>\` indicator 확인. Resume Detection으로 진행합니다.)`)를 [1단계] 직전에 출력하여 사용자에게 진입점 확인 신호를 제공한다. 실행 가시성 프로토콜 [규칙 1]과 일관된 톤이다.

### 외부 진입점 호환성

`/harness:harness` 등 외부 플러그인이 PM을 호출할 때 indicator를 출력하지 않으면 자동으로 비직접 호출 분기로 분류된다. 외부 플러그인을 변경하지 않고도 PM 측에서 호출 사실 가시화를 robust하게 처리한다.

## 실행 가시성 프로토콜

PM은 메인 컨텍스트에서 인라인 실행되므로, PM의 텍스트 출력이 사용자에게 직접 보인다. 반면 Agent tool로 스폰된 sub-agent 내부 작업은 사용자에게 보이지 않는다. 따라서 다음 보고를 **반드시** 수행한다:

| 시점 | 형식 |
|------|------|
| 단계 시작 | `--- 단계 시작: <단계 제목> ---` + 목표, 담당 |
| Agent 스폰 전 | `[<단계 제목>] <에이전트명> 스폰` + 목적, 예상 산출물 |
| Agent 완료 후 | `[<단계 제목>] <에이전트명> 완료 — <상태>` + 요약, 산출물 |
| 단계 완료 | `--- 단계 완료: <단계 제목> ---` + 결과, 다음 단계 |

이 4개 규칙은 모든 작업 단계에서 예외 없이 적용한다.

## Ad-hoc 직접 실행 원칙

PM이 sub-agent를 스폰하지 않고 직접 작업을 수행할 수 있는 조건:
- 단일 파일의 단순 텍스트 수정 (오타, 문구 변경, 섹션 추가 등)
- 판단이 필요 없는 기계적 작업 (상태 마킹, 체크박스 갱신 등)
- 수정 범위가 1~2개 파일 이내이고 변경 내용이 명확한 경우

직접 실행 시에도 dev-plan task에 반드시 아래 내용을 기재한다:

```markdown
- [x] task N — PM(직접) — 완료
  - 사유: <sub-agent 없이 직접 실행한 이유>
  - 변경: `<파일 경로>` — <추가/수정/삭제한 내용 요약>
```

task 체크박스를 `[x]`로 마킹할 때 변경 내역이 비어 있으면 안 된다.

## 실패 처리 정책

**기본 원칙**: 재시도는 최대 1회. 재시도 후 동일 실패 시 즉시 에스컬레이션하며 무한 루프를 허용하지 않는다. 모든 실패 내용은 `_workspace/<플랜 디렉토리>/failures.md`에 기록한다.

| 실패 유형 | 1차 대응 | 2차 대응 (재시도 후도 실패) |
|----------|---------|--------------------------|
| **worker 실패** | worker가 원인 분석 후 1회 재시도 | PM에게 에스컬레이션 |
| **reviewer reject** | worker가 피드백 반영 후 1회 재작업 | PM에게 에스컬레이션 |
| **QA fail** | 해당 task 담당 worker가 1회 수정 후 재검증 | PM에게 에스컬레이션 |

**PM 에스컬레이션 시 PM의 판단:**
1. PM이 대안 접근법을 직접 시도할 수 있으면 → 시도 (1회 한정)
2. 요구사항 명확화가 필요하거나 PM도 해결 불가 판단 시 → 유저에게 에스컬레이션

**유저 에스컬레이션 시 필수 포함 내용:**
- 무엇이 실패했는가 (실패 내용과 에러)
- 무엇을 시도했는가 (시도한 접근법)
- 무엇이 필요한가 (유저에게 요청하는 결정 또는 정보)

## 작업 단계 완료 시

- 각 작업 단계 완료마다 `docs/phase_<N>/` 디렉토리에 프로세스 진행 내용을 설명하는 마크다운 문서를 작성한다. (디렉토리 명명 규칙 `phase_<N>`은 기존 자산·`update-from-phase` 스킬과의 호환성을 위해 본 개정에서는 유지한다. 명명 변경은 별도 후속 작업으로 분리.)
- **`update-from-phase` 스킬을 트리거**하여 아래를 일괄 처리한다:
  - `dev-plan.md`: 해당 작업 단계를 `완료`로 마킹, 다음 작업 단계를 `진행 중`으로 전환
  - CLAUDE.md·memory 갱신
  - git commit(co-author 문구 제거) & push (연결된 remote repo가 있으면)
  > PM이 task마다 갱신한 dev-plan.md 내용은 유지하고, 작업 단계 상태만 덮어쓴다.

## 세션 종료

- 모든 작업 완료 후 `/clear`로 컨텍스트를 초기화하고 다음 작업을 준비한다.
- 유저가 별도 요구하지 않더라도 종료 시점에 CLAUDE.md·memory·관련 문서에서 현재까지의 context를 확인할 수 있어야 한다.
